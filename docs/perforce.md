# Perforce / P4 Code Review

## Automatic submitted indexing worker

`openreview p4 watch` discovers the latest visible submitted changelist across the selected project's native positive views using `p4 changes -s submitted -m 1`. It verifies the configured SSL server ID and bot identity before/after discovery, pins native fstat metadata at that submitted change, respects ordered project exclusions and checks native views again. Only metadata is uploaded; hosted indexing independently reads pinned source, verifies digests and reuses unchanged file caches. No checkout, shelf, submit or native approval is changed.

First log in with an existing workspace administrator API key using `openreview login`. Keep the key in the owner-only CLI configuration. Set P4USER/P4PASSWD using your secret manager to the dedicated bot and existing ticket, and establish SSL trust manually through your operator. Do not put tickets in command arguments. Authorize the Code Review hostname in the worker's SCM_ALLOWED_HOSTS. Then run:

```sh
openreview p4 watch --server ssl:HOST:1666 --server-id NATIVE_SERVER_ID \
  --url https://code-review.example --project PROJECT \
  --repository OPENREVIEW_REPOSITORY_ID --interval 300 --once
```

Replace the server identity with the value verified from your native server and use the selected repository ID from Settings → Code providers. Remove `--once` and run under your process supervisor for continuous operation. Intervals are 60–3600 seconds, default five minutes. Busy hosted indexes are skipped; unchanged ready inventories are not uploaded. Every iteration checks current administrator/connection access before native reads. Three consecutive failures stop the worker visibly; restore access/trust/tickets or fix the reported dashboard indexing failure before restarting. SIGINT/SIGTERM stop after the current bounded read operation. If the process stops, submitted indexing stops; this release does not claim a hosted worker heartbeat. Native protections can hide files/changes and their unknown coverage remains explicit.

The authenticated no-store `GET /api/p4/index?repositoryId=…` provides current project/instance/index status to this worker; viewer, other-workspace, disconnected and suspended access fail closed. Existing POST metadata upload remains compatible. Baselines cannot move to a lower submitted change or silently switch native server IDs. A server migration requires explicit operator reconnection/reselection.

A failed hosted index stops watcher retries rather than silently creating fresh jobs each cycle. Inspect the dashboard error, restore the underlying native access/source condition, and perform an explicit `openreview p4 index` / `openreview p4 upload` retry before resuming continuous watching.

A successfully completed authorized baseline automatically replaces the generation of already enabled review polling, clears stale leases/cursors, and cancels unfinished automatic reviews at the old baseline. Completed history and separately requested manual runs remain preserved; manual workers still enforce their original baseline. Disabled polling is never enabled by an upload or watcher. Changed connection credentials or a revoked polling administrator cannot authorize adoption; an administrator must explicitly restart polling with current access. This supersedes older instructions requiring a manual polling restart after every baseline refresh.

Contract tests cover discovery/metadata-only transport, unchanged/busy skips, failed authorizations and native diagnostics, atomic baseline adoption, stale-worker cancellation, disabled-poll preservation and backwards/server-mismatch rejection. The existing native acceptance server also passed real submitted discovery/fstat with zero source-body reads or inference. A temporary continuous native CLI process now passed changed submit → hosted incremental index → already enabled polling baseline adoption → automatic review/publication. Persistent supervisor hosting and the remaining recovery matrix still require acceptance; no native automatic approval is claimed. See [incremental acceptance](internal/p4-incremental-acceptance.md).

Settings → Code providers accepts an HTTPS P4 Code Review (formerly Swarm) URL and a dedicated bot’s P4 login ticket. The operator must allow that host in `SCM_ALLOWED_HOSTS` on both web and Convex deployments. The credential is JSON with exactly `username` and `ticket`; no password field is accepted. Obtain the ticket using `p4 -p <server> -u <bot> login -p` and manage its expiry/revocation in P4. Do not place tickets in URLs, logs, or source control.

Connection setup verifies the native project inventory before saving encrypted credentials. Workspace administrators can inspect current project IDs, branch IDs and depot views, then connect selected projects. Selection re-fetches the native catalog and rejects unavailable IDs. Each project creates a workspace repository scope and a team keyed by provider, instance and native project ID; existing assignments and settings survive repeated selection. Team access, inherited settings and repository rules use the existing workspace controls. Native P4 memberships are not imported. Disconnect removes the stored credential. Project access is not mapped to a fake Git remote or default branch, and connected projects remain disabled for generic Git automation. The separate native polling control is opt-in. Generic enable/index controls are rejected because native depot indexing requires an explicit submitted baseline; manual submitted-revision uploads and archived-shelf reviews are supported as described below. Repository settings remain editable without enabling reviews. This catalog does not claim initial indexing is complete. Configure P4 protections and private project membership to restrict the bot to intended sources.

Each accessible project offers **Inspect native reviews** with author, description, native state, shelved/submitted status and update time. Older/latest links use native review cursors. The authenticated `providerJobs.p4Reviews` action rechecks workspace admin access, active connection, project access and branch identity on each request. Short pages retain their cursor; empty pages with a cursor and cursors that could skip returned IDs fail visibly. Inspection does not enqueue model calls or enable automatic review processing.

`src/perforce.ts` also reads review pages, archived shelf manifests, digest-checked source and complete revision-pinned file diffs. Pending reviews without an archived changelist fail visibly. Native inventories can hide files according to server protections; their unknown coverage is retained. Truncated inventories/diffs, duplicate identities, invalid views, mismatched content origins/digests, and revision changes are rejected.

Native branch views are evaluated in order, separately for each participating branch. Snapshot identities include the selected branch IDs and ordered views, so changes in branch scope invalidate publication.

The adapter can publish revision-bound inline findings followed by a summary. It validates native diff lines, publisher identity, review version, depot file and right-side anchor. Comment retrieval includes archived comments and fails closed on incomplete pagination (100 per page, at most 5,000 scanned). A retry resumes accepted inline writes after a lost response; archived publications are not resurrected. The native API has no atomic idempotency guarantee: hosted manual dispatch uses durable worker leases and rechecks authorization before each native publication operation. External acceptance must still verify native retry behavior.

Native manual review, review polling, personally scoped follow-ups, local P4 bridge launch and opt-in runtime validation are implemented in the sections below. Automatic submitted-depot inventory and authorized cross-repository context are implemented with the native evidence below. Provider approval remains incomplete. Agent completion and the full OS/agent matrix remain unverified. Native acceptance evidence and remaining limits are recorded at the end of this document. Live acceptance requires a reachable P4 Server and P4 Code Review instance, a bot ticket and a disposable project with archived shelved reviews. Contract checks do not establish external acceptance.

## Native submitted-revision index

The local CLI now builds the shared symbol/import graph from all eligible files in the selected project's depot views:

```sh
openreview p4 index --server ssl:p4.example:1666 --server-id main \
  --url https://code-review.example --project payments --change 42 \
  --output payments-index.json
```

Set `P4USER` and `P4PASSWD` to the dedicated read-only bot identity and ticket. Allow the Code Review host through `SCM_ALLOWED_HOSTS`. Install the official P4 CLI, establish the server's SSL trust independently, and obtain the native server ID from your administrator. The configured P4 Server must be the one backing that Code Review instance. No password or ticket is put in command arguments or output; the command never changes SSL trust, client workspaces, shelves, depot files or changelists. Local P4 config and cached tickets are isolated from the invocation so another checkout's configuration or credential cannot silently authorize it.

The command verifies the actual server/user and a submitted changelist, retrieves revision-pinned `fstat` manifests through fixed CLI arguments, honors project exclusions and explicit re-inclusions, and reads each eligible file at its native revision with keyword expansion disabled. Native print bytes must be valid UTF-8 and match the depot digest; unsupported encoding or client conversion fails visibly. Every file must match the recorded native MD5 and size before the existing shared indexer receives it. The Code Review project is fetched again before saving to reject changed views. The output has owner-only permissions and refuses to overwrite an existing file.

The artifact retains native server, project, changelist, manifest revision, skipped-file reasons and coverage limitations. Paths are depot-relative to preserve depot identity and allow import resolution. Server protections can hide files; project-specific ignore files are not applied automatically. Current bounds are 100 include patterns, 10,000 inventory records, 200 KB per source file, 20 MB of source, 8 MB per metadata response and 60 seconds per native command. Metadata replacement characters, missing digests, unexpected encodings or changed source fail visibly. This local command does not activate automatic reviews. Its metadata inventory can be uploaded for durable hosted indexing as described below; automatic depot polling and native acceptance remain incomplete.

Native references: [tagged JSON and explicit authentication](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/global.options.html), [revision-aware inventory](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_fstat.html), and [pinned printing, line endings and keywords](https://help.perforce.com/helix-core/server-apps/cmdref/current/Content/CmdRef/p4_print.html).


## Native archived-shelf review

The CLI can now combine that submitted project baseline with an archived shelf and run the existing shared review engine:

```sh
openreview p4 review --server ssl:p4.example:1666 --server-id main \
  --url https://code-review.example --project payments --change 42 \
  --review 57 --mode standard --output payments-review.json
```

`--change` explicitly selects the submitted comparison/context baseline; `--review` is the native P4 Code Review review ID. It must be open with an archived pending shelf. Configure the existing `LLM_*` environment variables for inference. The command reads through the same bot identity and native CLI checks as indexing, preserves native revision identities rather than inventing Git SHAs, and overlays archived additions/edits/deletions on the baseline. Unchanged caller files participate in shared graph retrieval. Diff headers and right-side source are checked by the native adapter; left-side context must match the indexed baseline before inference. A missing readable baseline, changed views/revision/state or unmatched diff fails visibly.

Excluded changed sources are removed from the context instead of leaving stale baseline code, with coverage reasons recorded. Binary and secret files are not fetched as review source. The final native shelf is checked again after inference. Output is owner-only and refuses overwrites before making model calls; it records the native server/project/review/version/change, submitted comparison revision, findings, review score, diagnostics and model usage. It does not publish, approve, submit, change a workspace or modify a shelf. The chosen baseline is not claimed to be an automatically discovered common ancestor. Select the correct submitted baseline for the review's depot views.

This provides tested native shelf ingestion and shared engine execution, not the hosted application pipeline. Follow-ups, P4 bridge fixes and native live acceptance remain outstanding. Hosted dispatch/publication and optional durable native review polling are described below. Their contract checks do not establish live acceptance.


## Manual hosted indexing

After connecting and selecting the native project in Settings → Code providers, create an OpenReview API key as a workspace administrator, use `openreview login`, then upload a newly generated native index artifact:

```sh
openreview p4 upload --input payments-index.json --repository <OpenReview-repository-ID>
```

Find the OpenReview repository ID in `GET /api/repositories` using that API key; it is distinct from the native P4 project ID. The upload uses the existing CLI login origin and revocable API key. It sends only the Code Review instance and canonical native metadata inventory, including project views, submitted changelist, file revisions, sizes and digests. Local indexed source bodies, ticket, symbols and review findings are not uploaded. Old artifacts without the new `inventory` and `codeReviewInstance` fields must be regenerated. The API endpoint is `POST /api/p4/index`; it returns HTTP 202 with `jobId`, `revision` and eligible file `total`. Completion is asynchronous. Inspect indexing status, skipped paths, retries and indexed revision using the existing repository settings detail.

The hosted bot must reach the Code Review HTTPS instance and have read access to the pinned files. The backend rechecks current admin access, connection/instance/project identity and current native project views, recomputes the inventory revision, then independently retrieves every new source at `#<file-revision>` through the native API. File metadata, content origin, byte size, MD5 and UTF-8 decoding must agree before the shared graph/chunk indexer stores it. Project scope is checked before/after source retrieval and before completion. Existing same-file revision caches can be reused. The manifest hash establishes identity, not the completeness or authenticity of an operator-enumerated depot inventory: the administrator is trusted to select the correct backing server and submitted baseline. Protections can hide inventory, and project ignore files are not applied automatically.

Durable jobs use the existing 20-file batch, retry and recovery system, with atomic batch leases preventing overlapping retry/recovery writes. Each mutation checks the current requesting admin and the active original provider connection/credential generation. Removed membership, disconnected/suspended access or replaced credentials stop future writes and completion. Dirty local workspaces are never changed by indexing. The CLI reads at most 40 MB of local index artifact. Upload bounds are 750 KB metadata, 8,000 records, 200 KB per source and 20 MB eligible source; exceeding a bound fails explicitly. The local native inventory ceiling remains 10,000 records. Manual indexing leaves automatic reviews disabled. It does not itself request a review, launch fixes, run checks or approve changes. A reachable real P4 installation remains required for live acceptance.


## Hosted archived-shelf preparation

Completed native index jobs retain their canonical metadata manifest. The private `p4ShelfJobs.prepare` action loads only a completed current baseline and verified stored sources. It checks current requesting-admin access, active connection, original credential digest and exact indexed revision before loading files, and repeats these checks after native shelf ingestion. A new/restarted index, replaced source identity, changed credentials or revoked membership rejects preparation. The action accepts an optional exact archived revision and explicit baseline job ID; it returns private artifact metadata rather than source bodies.

`src/p4-shelf.ts` provides one shared ingestion implementation for this action and `openreview p4 review`. It overlays native archived additions/edits/deletions, compares the complete diff's left-side context with the indexed submitted baseline, preserves unchanged caller context, and records native versions/archive changes/base file revisions. Excluded changed sources are removed from baseline context. Persisted changed source and diff text are redacted. Project/view/state/revision changes, unmatched or unavailable baselines, unexpected source identities and context over 20 MB fail visibly. Baseline manifests predating retention must be regenerated by uploading a fresh index.

This internal preparation step makes the hosted baseline/shelf input available to durable review dispatch. It does not itself run inference, publish comments, expose a user-facing review trigger, enable automatic polling, launch an agent or approve a change. The dispatchers below supply inference/publication and opt-in review polling; agent launching, approval and native external acceptance remain outstanding.

Optional `force: true` creates a new review at the current shelf revision. Ordinary duplicate requests reuse the existing current run. No source content or ticket is accepted from that request.

Preparation pins the archived native shelf to the completed baseline. A durable worker applies effective review settings, custom rules, learned preferences, existing finding assessment and referenced issue requirements through the shared review engine. It saves findings, diagnostic coverage, structured summary and model calls before publication. Review revisions remain native opaque IDs, not invented Git SHAs. Results appear in Pull Requests with history and processing stages; Re-review current PR dispatches a fresh native request. View/Re-review and Fix links are published. Fix requires the latest completed review with eligible unresolved findings and a matching registered native client.

Recovery waits for live leases. Native publication rechecks authorization and integration scope before each operation. Changed or closed shelves cancel obsolete reviews; revoked access prevents inference/publication and stops after bounded retries. Persisted results allow a publication retry without repeating analysis. This workflow does not enable automatic polling, cross-repository retrieval, P4 agent fixes, runtime checks or automatic approval. ## Durable native review polling

After indexing completes, a workspace administrator can **Enable review polling** in Settings → Code providers. This is separate from generic Git indexing/enable controls and starts disabled. **Restart / retry polling** selects the current completed submitted baseline and records a new authorization generation. **Disable polling** cancels that generation’s queued automatic reviews and pending polling steps, while preserving separately requested manual reviews. No credential is accepted by these controls; the existing encrypted native connection and current admin identity authorize the job.

A durable cursor walks every visible review page in creation order, including older reviews whose archived shelf changes later. One step fetches a page or processes one native review; subsequent steps wait four seconds, and a complete inventory restarts after five minutes. Large inventories take correspondingly longer to finish. Each page/row checkpoint and scheduler identity is persisted. A worker uses an expiring lease; recovery reuses live jobs, replaces expired work, and rejects stale worker mutations. Native private-project/server protections may hide reviews or files, so the UI does not claim complete server-wide coverage. Native API [review ordering and pagination](https://help.perforce.com/helix-core/helix-swarm/swarm/2026.1/Content/Swarm/swarm-api-endpoint-reviews.html) define the cursor; updated-day ordering is not used because it can ignore the native page-size bound.

Polling checks native current project branches and review state before dispatch. The shared Automatic review and Re-review settings apply. Target/ignored branch globs match the native branch IDs associated with the selected project; this provider has no Git head/base branch pair. New opaque revisions enqueue the existing archived-shelf worker. The same already queued/completed/failed revision and baseline are not repeatedly analyzed; a failed run remains available for explicit manual retry. Closed/submitted/archived reviews cancel unfinished work. Shelves without an archived pending changelist are recorded as skipped without inference, with recent reasons visible in the portal.

Current admin membership, repository access, original connection/credential digest, completed baseline and polling generation are rechecked at queue/save/publication boundaries. Automatic settings changes also prevent subsequent automatic analysis/publication. Re-indexing, replaced credentials or revoked admin access require an explicit administrator restart using the new trusted baseline. Errors persist with at most three polling attempts before visible failure; a failed poll is not restarted by recovery. The inventory ceiling is 100 nonempty pages / 10,000 visible reviews; a terminal empty page is permitted to prove completion at the ceiling. Exceeding it fails visibly. Recovery currently inspects at most 1,000 enabled native projects.

Portal status includes current page/cursor/row, cumulative scanned/skipped counts, recent skipped reasons, next step, last completed inventory and failure attempts. The last completion time is only written after the entire inventory finishes; it does not hide an unfinished or failed scan. This feature does not poll submitted-depot inventories, run P4 agent fixes/runtime checks, approve or merge changes. Contract tests cover older-shelf revision detection, duplicate suppression, leases/recovery, policy/generation revocation, branch filters, missing archives and pagination/coverage failures. External acceptance still requires a reachable P4 installation and disposable native review.

### Register a native local checkout

  --server ssl:p4.example.com:1666 --client YOUR_CLIENT \

Automatic approval remains unavailable for Perforce. The documented state-transition request has no revision parameter; the version guard belongs to voting.
