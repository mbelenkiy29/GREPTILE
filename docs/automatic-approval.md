# Opt-in automatic approval

Automatic approval is disabled by default. Workspace admins configure trusted policies in Settings → Runtime & Approval. Organization defaults apply to teams and repositories unless explicitly overridden; Sync from parent removes an override. Repository text and PR instructions cannot enable approval. Enabling a policy applies to completed reviews; re-review an existing PR to request an assessment under the current configuration.

The gate compares both the current head and any provider-native revision key (such as a base/start version tuple) with the reviewed revision, then requires a current open non-draft revision, the latest completed review, explicit complete coverage, no unresolved verified findings, structured assessment confidence exactly 1, known risk at or below the configured ceiling (low by default), no excluded author/path, no active human change request, and passing required checks. Legacy reviews without an assessment or coverage record cannot qualify. Required runtime validation uses a passed durable job matching the current approved image/command policy and exact revision; manually attached evidence alone cannot satisfy it.

GitHub Cloud, GitHub Enterprise, Gitea, GitLab, Cursor Origin and Bitbucket Cloud/Data Center implement native approval and dismissal. Other adapters currently return a visible unsupported state. Repository-specific controls list supported connections. GitHub's native required checks combine classic branch protection and active rulesets, including an explicitly required GitHub App identity. Additional checks can be configured by name with an optional App ID. Missing, pending, failing, neutral, skipped, or contradictory required checks block approval. GitHub legacy status contexts require Commit statuses: read permission; named checks pinned to an App ID use Checks: read. Protected-branch inspection may require Administration: read. Missing access is a visible failure, never an empty required-check list.

Gitea uses the effective branch response's required status contexts and the exact head's combined latest statuses. This is verified against Gitea 28. Protected branches on versions that omit effective-check fields fail closed. Exact names and simple `*`/`?` native status patterns are supported; more complex patterns produce an explicit verification error. Every matching status must pass, and a pattern with no match blocks approval. GitHub App IDs cannot be satisfied by a Gitea status. Native `REQUEST_CHANGES`, `dismissed` and `stale` review fields are normalized; a comment review cannot clear a human objection. Approval uses Gitea's `APPROVED` event, only reuses the connected bot's active exact-head marker, refuses the bot's own PR, and confirms dismissal by reading `dismissed: true`. See the [Gitea approval API](https://docs.gitea.com/api/operations/repo-create-pull-review/) and [dismissal API](https://docs.gitea.com/api/operations/repo-dismiss-pull-review/).

GitHub Free does not offer rulesets on private repositories. Only GitHub's explicit plan-unavailable response combined with a confirmed unprotected branch establishes that no active native branch rules apply. Generic 403/404 errors still block verification. Configured OpenReview required checks continue to apply. See [GitHub ruleset availability](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

Jobs use transactional leases, exact head commits, current trusted settings, and bot-owned publication markers. A retry can recover an existing native approval after a lost response without publishing a duplicate. Native receipt IDs are persisted before post-publication reads. Verification errors trigger immediate withdrawal; failed withdrawals retain a visible revocation_pending state and retry with the same native receipt. A pending withdrawal is never converted back into approval merely because the gates recover. Unknown receipts are recovered only through the exact job marker, bot identity and reviewed head; unavailable or ambiguous reads remain pending. Legacy failed jobs with native receipt IDs also withdraw on retry. Native providers may be unavailable or revoke permission, so withdrawal cannot be guaranteed while those failures persist; the portal displays that the native approval may remain active. State is rechecked immediately before and after publication; a changed revision, policy, human objection, runtime requirement, or finding invalidates an approval. PR/review webhooks trigger rechecks; a five-minute sweep also recovers interrupted jobs, waits for required checks, and revalidates active approvals. The sweep traverses every eligible status through bounded 100-job cursor pages, including pending withdrawals, so older live leases cannot hide later expired work.

Provider reads and database writes cannot be atomic. An approval can briefly exist during a concurrent change until the recheck/dismissal completes. GitHub records its exact commit. Native dismissal permission errors remain visible and are retried; an administrator may need to dismiss the review in GitHub. Branch protections that dismiss stale approvals provide additional provider enforcement. OpenReview never calls merge APIs.

Current verification: contract checks for native requirements/identity, positive gates, failures, duplicate claims/publications, human objections, stale revisions, policy races, inheritance and viewer isolation pass. A read-only live check on acceptance PR #4 retrieved the installing bot identity and current revision/requirements without publishing an approval. A real failed-runtime PR #4 review also produced a blocked durable approval job after native provider reads, with explicit failed-runtime, unresolved-finding and risk-ceiling reasons. Native GitHub reviews remained unchanged and the temporary repository policies were restored. The separate positive GitHub acceptance created a native exact-revision approval for PR #3, reused it on replay, then invalidated and dismissed it after an exclusion-policy change; evidence is in ignored `output/setup/runtime-positive-approval-acceptance.json`.

Hosted Gitea acceptance executed the exact revision through a durable runtime job and then evaluated the real approval policy. The assessment was 99%, so approval correctly remained blocked on maximum confidence. Policies were restored and no approval/merge was published. A native temporary branch rule and explicitly synthetic status context verified pending, failure and success mapping; the rule was removed and its prior empty configuration verified. These status fixtures are not CI execution evidence. Positive Gitea approval/dismissal publication, additional provider implementations and the complete OS/provider matrix remain outstanding.

GitLab reads exact-head/source-branch latest commit statuses and trusted project merge requirements. Missing required pipelines, unresolved required discussions, failed external status checks, human change requests, conflicts and unfinished native merge checks block approval. Native external checks are read only when the project requires them; unavailable licensed APIs fail visibly. GitHub App IDs cannot be satisfied by GitLab status contexts. Approval uses the native approve endpoint with `sha`, then verifies the native version and stores a bot-owned receipt containing head, base/start revision and native `approved_at`. A comment alone is not an approval. Replay requires both the intact receipt and matching current native bot approval. Withdrawal uses only the authenticated bot's unapprove endpoint and never resets all approvers. An old receipt cannot withdraw a newer timestamp. See [GitLab approvals](https://docs.gitlab.com/api/merge_request_approvals/), [commit statuses](https://docs.gitlab.com/api/commits/#list-commit-statuses), and [external status checks](https://docs.gitlab.com/api/status_checks/).

GitLab versions without native approval timestamps fail closed. A lost approve response without a completed receipt requires inspecting/removing the bot approval before retrying. A known approval followed by a failed receipt write is withdrawn if its timestamp still matches; re-review creates a fresh job/marker after recovery. Native permission, response-validation and withdrawal failures remain visible. Completed publication also requires a fresh active bot approval readback in the shared worker.


Cursor Origin uses fresh expected-head mergeability and native version-bound approval reviews, retaining opaque native review IDs in durable jobs. See [Origin approval safeguards and current acceptance](origin.md#opt-in-native-approval). This adapter is contract-tested; no live Origin approval is claimed.


Bitbucket Cloud reads the unfiltered native mergeability-check collection and exact-head commit status keys. State, authenticated-user permission and Git eligibility checks must be present; required or blocking standard/custom/queue checks must pass. Unknown, pending, skipped, incomplete, contradictory or unavailable checks fail closed. Optional nonblocking failed checks are not promoted into requirements. Required minimum-approval checks are conservative: the current native threshold must already pass before OpenReview adds its approval. The API does not exhaustively certify all conditions of a future merge, and OpenReview never attempts one. Configured checks use native status keys; GitHub App IDs cannot be satisfied by Bitbucket statuses.

Approval uses the verified Forge app publisher. OpenReview preserves current reviewer decisions without inventing a reviewed commit: Bitbucket participants expose a native action timestamp but no reviewed SHA. Current human/unknown-account change requests block approval. Native approval publication is guarded before/after against open, non-draft, unqueued state, both source/destination identities and revisions, author identity, and objections. Its bot-owned top-level receipt records the head, destination revision and native approval timestamp. Only an intact receipt plus matching active native app approval can be replayed or withdrawn; old receipts cannot withdraw newer timestamps. Lost approval responses or missing native metadata require native inspection; known approvals are withdrawn after receipt or revision races. Errors remain visible.

The Forge manifest requests read/write PR scopes and subscribes to reviewer-status updates, including clear-on-new-source events. Those events recheck existing approval jobs without model reviews; PR updates/closure also trigger rechecks, and the shared sweep checks statuses/policies. Signed event hashes may be abbreviated; exact revisions and actual reviewer decisions always come from native API reads. Installed Forge permissions, delivery, publishing, replay, withdrawal and all live gates remain unverified. These paths are covered by native-response fixtures and the durable provider factory/coordinator. See [Bitbucket approvals and mergeability API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/) and [Forge reviewer events](https://developer.atlassian.com/platform/forge/events-reference/bitbucket/).


Bitbucket Data Center uses explicit native publisher/PR metadata, exact source-commit status keys and read-only merge vetoes. Its participant PUT supplies the reviewed commit and PR version; receipts retain the newly observed native approval activity ID. Replay and withdrawal require matching publisher-owned native decisions. Missing/ambiguous responses require native inspection; known receipt failures invoke guarded cleanup, with errors visible. Native version/decision races and actual instance acceptance remain unverified. See [Data Center safeguards and acceptance](bitbucket-data-center.md#opt-in-native-approval-implemented-live-acceptance-pending).

Approval diagnostics require current reader access to every repository captured in the review's cross-repository context. Losing a source-team membership denies this endpoint even if the primary repository remains accessible; restored membership permits it again. Native Perforce transitions can now be inspected from Code Providers, but native transition availability is not OpenReview approval eligibility. Perforce automatic approval remains unavailable because complete permission-independent review coverage and safe native vote ownership have not been established.
