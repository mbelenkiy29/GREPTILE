# Active runtime cancellation after credential rejection

October 4, 2026. A worker heartbeat previously logged a revoked/expired credential but continued the active snapshot or container. The worker now aborts active work when the server returns its explicit credential-rejection code, stops heartbeats, and exits with supervisor status 78. Snapshot rejection likewise stops without attempting a result report. Ordinary transport failures retain the existing retry behavior.

The sandbox accepts an optional cancellation signal. Pre-aborted work never starts Docker; cancellation destroys the archive stream, kills the attached Docker process, and forcibly removes only the exact generated container. It rejects instead of recording successful execution evidence. The returned rejection occurs after cleanup.

Verification includes controlled HTTP credential-rejection tests, an exact-container subprocess cleanup test, and actual Docker execution in the isolated Linux VM. The native probe ran the approved GitHub PR #4 archive at `40d7a953b03946632f2e643096b4227b6a705483` in the existing digest-pinned Node image, started a bounded synthetic sleep command, aborted it, and verified the container no longer existed. Its transient systemd unit used the runtime identity, Docker supplementary group, no-new-privileges, strict system protection, private temporary directory and protected home. This is operator acceptance, not recorded hosted runtime evidence or actual hosted credential revocation.

Process inspection authoritatively confirmed the inner command and sleep were running; the final probe uses that signal and exits 0. These earlier attempts remain in separate logs and do not count as acceptance passes. Every probe cleaned up its container. The permanent worker remains disabled and inactive; no credential or runtime/approval policy was granted or changed.
