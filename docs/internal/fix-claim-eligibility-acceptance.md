# Revalidate selected findings before agent dispatch

October 4, 2026. Fix and Fix All previously selected eligible findings when creating the five-minute request, but bridge claim checked repository/review authority without rechecking that selection. Resolving/dismissing a finding or changing the confidence policy between creation and claim could leave an obsolete prompt eligible for dispatch.

New requests record `findingIds` alongside the existing exact revision and prompt. Both the initial claim-data read and the final atomic claim require every recorded finding to still belong to that repository, organization, PR, completed latest review and revision, remain open, meet the current effective confidence threshold and be readable through every evidence source repository. New findings are not silently added to an existing selection. If any selected finding becomes ineligible, the user must create a fresh request. Agent launch still does not resolve findings.

The optional schema field preserves historical launch/report records. Unbound pending requests are rejected instead of inferring authorization from prompt text. A deployed readonly check found zero unexpired pending requests before this migration (`output/setup/fix-claim-live-pending-before.json`). Existing paired devices and registered/dirty checkouts are untouched.

`bridgeJobs.claim` now includes initial validation in its error handler. A still-authorized stale-selection or legacy request records a visible failure with an explicit “no agent was launched” message. Revoked repository/source authority cannot be used to overwrite a successful claim or reveal its context. Requests with revoked authority may remain pending until expiry; the claim endpoint still rejects them and the local bridge reports the failed claim. Old completed/launched requests can still report normal process completion.

Regression evidence covers Fix All selecting only sufficiently confident findings; resolved/dismissed status and a raised inherited threshold; resolution during provider fetch before final claim; legacy rejection before any provider read; source-team viewer access revoked after creation; duplicate claims/reports and existing bridge lifecycle. The source-evidence access fixture deliberately isolates finding evidence without a review-context receipt so that the new finding-reader check is actually exercised. It is a controlled authorization regression, not a new published context review.

The first attempted new test fixture failed schema validation because its description/evidence were incomplete; that setup was corrected. It is not claimed as a before-fix behavioral failure. The gap was established by inspecting the former claim code.

No new live agent run, paid inference, finding resolution, commit or push is claimed for this change. Native Fix All multi-finding launch, human-pushed resolution and the full OS/provider acceptance matrix remain required.
