# Linux protocol launcher argument escaping

October 4, 2026. Corrected the native Linux desktop entry generated by `src/bridge-install.ts`. The installer previously used JSON quoting for Exec paths. Desktop entries apply string unescaping, argument quoting and URI field-code expansion; JSON quoting does not preserve every path through these stages. The official [freedesktop Exec specification](https://specifications.freedesktop.org/desktop-entry/latest/exec-variables.html) defines the required escaping.

`desktopExecArgument` now quotes reserved arguments, doubles the escapes needed for backslashes/quotes/dollar signs/backticks, and escapes literal percent signs as `%%`. Only the standalone `%u` URI argument remains a field code. Control characters in paths and an equals sign in the executable path are rejected before installing an invalid launcher. macOS and Windows adapters retain their existing behavior. No repository content is interpreted as a command or passed through a shell.

## Actual Linux parser check

The already-isolated Ubuntu 26.04 aarch64 VM has native GIO desktop APIs and Node 24.7. The test used a disposable recorder script whose path contains a space, dollar sign, backtick, quote, and literal `%u`. The old generated Exec line was rejected by the native `Gio.DesktopAppInfo` constructor. With the correction, the same clean test parsed and launched the recorder, receiving exactly `bridge`, `dispatch`, and `openreview://fix?request=abcdefghijklmnop`. The receipt was removed before each run so an old file could not establish a false pass.

The fixture changes only Terminal=true to Terminal=false to isolate Exec parsing in a headless VM. It is an argument recorder, not a coding agent or the production bridge. This proves native Linux parser/argv behavior for that case; it does **not** prove installed MIME registration, a graphical terminal opening, browser protocol confirmation, agent launch/authentication, or a completed Linux Fix loop. Those remain acceptance requirements. An initial separate backslash-in-Node-script-filename attempt reached Node's own unsupported encoded-backslash module-path error; it is not a successful execution case. Backslash escaping itself has a local serialization regression, not a native Node script-launch claim.

The runtime worker remains disabled and has no credential file. No new software packages, access grants, agents, paid model calls, workers, runtime policies or repository pushes were created. Test artifacts were copied into the isolated guest's temporary directory; there are no host mounts.
