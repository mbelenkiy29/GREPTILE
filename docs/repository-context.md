# Cross-repository context

GitHub Cloud primary context matches the native PR author's immutable account ID and current login to the authenticated workspace account. Receipts retain that ID and revalidate it before cache/model/publication use; saved-publication retries also compare it with the current native PR author. A missing ID, recycled username, changed account or legacy username-only receipt cannot authorize source retrieval or republishing. Re-review creates a fresh receipt; after an account rename, sign in again to refresh the workspace login. Existing historical review read access continues to require access to all recorded source repositories.

Workspace admins explicitly select 2–20 repositories in Memory → Cross-repo context. Review authors must be linked to a workspace account and have access to every participating repository in a selected cluster. A cluster is omitted as a whole if the author lacks access to any member. Sources must have a completed, ready index. The reader uses indexed graph/search context, selects up to ten files per repository, and caps retrieved source at 100 KB. Coverage reports disclose these bounds and omitted sources.

Git providers fetch the tree at the selected indexed commit and each file by its native blob identity. Perforce sources require the author's separate personal native identity for that source repository and a verified submitted inventory. They are fetched with that author's ticket, never a bot ticket. P4 source links use the exact submitted file revision, while provenance also retains the submitted inventory identity. Native protections can hide files; inventory completeness is not measurable. Primary Perforce reviews require a linked native review author rather than assuming their native username is a GitHub account. Primary GitHub Cloud reviews use the authenticated GitHub workspace identity. GitLab, Gitea and GitHub Enterprise authors link a personal identity in Settings → Personal agents. Their authenticated profile supplies an immutable account ID; native review ingestion supplies the author ID, and both must match on the same provider connection. Username equality across services is insufficient. Other native providers still omit primary cluster context until their connection-specific author links are implemented. Their repositories can supply explicitly selected sources to authorized supported primary reviews. Completing remaining author adapters is implementation work.

Sources have unique paths containing repository and indexed revision, plus original repository, revision and source URL provenance. The shared engine retains provenance in evidence and cached model inputs. Published summaries list only fetched repository sources actually supplied to the review context, with bounded safe links; these links do not establish runtime execution. A prior cross-repository finding can inform a new review only when its exact pinned source was fetched again. Withheld prior findings stay unresolved and add a coverage limitation.

Authorization receipts record the review author, selected cluster membership, source provider identity and revision, connection credential identity, and any personal native identity generation and baseline. Cache access, model work, result saving and publication validate current scope. Native credentials, project views and fetched file access are checked again before model use and native publication. Changed clusters, source revisions, credentials, personal identities or team access require re-review. Saved result retries retain the receipt; legacy cross-repository results without one cannot be republished. Native failed saved results expose both Retry saved publication and Re-review current shelf.

The receipt is retained on the review as well as the private saved result. Review detail, review/finding lists, pull request summaries and Fix requests require the reader's access to all recorded participating repositories. Historical source links do not bypass current workspace/team access. Native provider comments remain governed by that provider's own audience; admins selecting a cluster authorize supplying its source to reviews in the selected repositories and must account for that native audience.

There is no provider write, branch update, commit, push or agent launch in context retrieval. Runtime archives contain only their primary repository; external context is not executed.

## Personal provider identities

An existing personal token needs authenticated-profile access (`read_user` on GitLab; `read:user` on Gitea; authenticated-profile access on GitHub Enterprise). Tokens are encrypted with authenticated scope binding to workspace, connection and user. Links expire after 24 hours, may fail earlier when the native token expires, and can be disconnected from Personal agents. Disconnect removes the credential and advances its generation. Linking requires writable workspace/team access; a provider account cannot be claimed by a second workspace user on the same connection. Workspace/team permissions continue to govern source retrieval.

The reader compares the immutable native PR/MR author ID with the linked identity, never falls back to a GitHub login or equal native username, and performs a fresh authenticated-profile check before model/cache use and publication. Blocked accounts, bots, native token revocation, account ID/name changes, link replacement, connection changes and workspace/team revocation fail closed. A saved result retry also compares the current PR/MR author ID. Viewer read access does not grant linking or model/agent execution.

Identity verification uses the official [GitLab current-user endpoint](https://docs.gitlab.com/api/users/#retrieve-the-current-user) and [Gitea current-user endpoint](https://docs.gitea.com/api/operations/user-get-current/). This is a personal identity link, separate from the admin-managed provider installation and local bridge pairing.

Live integration acceptance used the existing GitLab CE and Gitea fixtures: verified Alice author IDs, temporary explicit GitHub clusters, full deployed model review and native summary publication. Both retained five actual pinned source paths and passed native publisher/revision/body readback. Automatic recovery reused authorized cached work after model rate limits. Temporary links/clusters were removed afterward. Evidence is retained in ignored provider-context-review-evidence.json and the native context-review-portal.png screenshots. This does not establish remaining native author adapters or broad provider acceptance.

GitHub Enterprise Server uses its root or `/api/v3` API root. Dedicated GHE.com installations use `api.SUBDOMAIN.ghe.com` for API calls and `SUBDOMAIN.ghe.com` for source/clone links. An operator entering the web host must explicitly authorize the derived API host in `SCM_ALLOWED_HOSTS` before any credential is sent there. Enterprise personal linking uses [GitHub’s authenticated-user API](https://docs.github.com/en/enterprise-server%403.19/rest/users/users#get-the-authenticated-user). Bots and suspended accounts are rejected. Enterprise author linking has contract coverage; live acceptance requires an actual Enterprise installation and personal account and remains unverified.

Personal provider authority binds the provider kind, instance and encrypted connection credential as well as connection/user IDs. Instance replacement cannot reuse a personal identity merely because another server returns the same username and numeric ID. Links created before this stronger authority digest require re-linking. This does not change GitHub.com sign-in or separate native P4 links.

## Bitbucket Data Center personal identities

Authors link their existing personal HTTP access token in Personal agents. Read-only verification requests application properties, requires the authenticated `X-AUSERNAME` response header, then finds the exact active `NORMAL` user in native filtered user pages. A public profile or submitted username alone cannot establish the authenticated account. The resulting immutable user ID must match the native PR author on the same connection. The link shares encrypted credential storage, 24-hour expiry, generation-based revocation, instance-bound authority and workspace/team write restrictions with other personal provider links.

Missing/anonymous/changed identity headers, denied requests, inactive or service accounts, ambiguous results and invalid pagination fail. User lookup follows native cursors and is capped at ten pages of at most 100 users each; exceeding the bound fails visibly. All requests stay on the operator-authorized HTTPS instance, preserve its context path and reject redirects. Only the verified account's ID and name are retained; other user profiles are not saved as review context. Fresh verification runs before model/cache use and publication.

This follows [Atlassian's authenticated identity guidance](https://community.developer.atlassian.com/t/obtain-authorised-users-username-from-api/24422) and its [read-only filtered user API](https://docs.atlassian.com/bitbucket-server/rest/7.3.0/bitbucket-rest.html). The implementation has contract coverage. Live acceptance requires an actual Data Center instance, installation and personal token; header availability on that deployment remains unverified. No native integration claim follows from these contracts alone.
