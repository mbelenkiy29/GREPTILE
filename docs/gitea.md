# Gitea setup and live acceptance

Use a dedicated bot token with `write:repository`, `write:issue`, and `read:user`; include `read:organization` when discovering organization repositories. Grant the bot repository admin on selected repositories if follow-ups are enabled. Gitea 28 requires repository admin to inspect another author's native repository permissions; repository write alone returns HTTP 403. Instance administrator access is unnecessary. See the [native permission handler](https://github.com/go-gitea/gitea/blob/v28.0.0/routers/api/v1/repo/collaborators.go).

Authorize the HTTPS instance host in `SCM_ALLOWED_HOSTS` on both the web server and Convex backend. Connect through Settings → Code providers, select repositories, and enable indexing/reviews. Credentials are encrypted with `CREDENTIAL_ENCRYPTION_KEY` and scoped to the workspace and provider.

Allow the exact OpenReview callback hostname in Gitea’s `[webhook] ALLOWED_HOST_LIST` when outbound delivery is restricted; retain any existing required hosts and restart Gitea after configuration changes. Do not use a wildcard to solve delivery failures.

Create a native Gitea repository webhook using the connection's displayed URL and the same secret supplied during connection. Subscribe to pull requests (including synchronization), reviews, comments, and push events. The receiver verifies the exact body HMAC and records the native delivery identity before dispatching durable work.

Gitea 28 sends submitted comment reviews with the generic `pull_request_comment` header and `review.type: pull_request_review_comment`; both identifiers are validated. Direct inline replies arrive as `issue_comment` with `is_pull: true`. Native timeline responses omit code comments, so these replies are looked up by exact comment ID, body and author in the PR's scoped review records. Replies use the native `/pulls/{index}/comments/{id}/replies` endpoint; unsupported server versions fail visibly rather than publishing a general comment as a thread reply. Discussion lookup is bounded to 100 reviews.

## Publisher replay guards

GitHub Cloud/Enterprise and Gitea publication now check the current open head before both new publication and replay. Reuse requires the installing App/dedicated token publisher, the exact head commit, the completed comment-review state, and the terminal run marker. New finding anchors must be added lines in the current native diff and belong to the reviewed commit. Returned review identities are validated; finding mapping rejects human markers, wrong commits/review IDs/locations, quoted markers from bot replies, and missing native findings. The head is checked again after native comment retrieval, so a revision change cannot be reported as a successful current review. Native publication and a simultaneous push cannot be one transaction; already-sent requests may leave an older-commit comment, which fails the final current-head check.

Reply deduplication also requires the actual publisher and thread location. GitHub uses native `in_reply_to_id`; Gitea binds review ID, path and position. A marker copied into a human comment or quoted inside another bot response is not replay evidence.
