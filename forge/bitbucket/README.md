# OpenReview Bitbucket Forge app

This is the native app source, not an installed integration. Its Custom UI workspace settings page uses Forge's authenticated `invokeRemote` to submit an explicit, five-minute OpenReview connection code. It makes no connection request on page load, stores no code/token, clears the code after submission and reports suspended connections truthfully. Product events, hourly token refresh and pre-uninstall cleanup invoke the web backend directly.

Build from this directory with Node.js 24:

```sh
pnpm install --frozen-lockfile
pnpm build
```

Use the official [Forge CLI](https://developer.atlassian.com/platform/forge/getting-started/) and an authorized Atlassian developer account. For an existing registered app, export `BITBUCKET_FORGE_APP_ID` as its exact app ARI and `OPENREVIEW_URL` as the canonical HTTPS OpenReview origin. The manifest resolves these through Forge's supported environment variables. Do not put credentials in either value.

For a first registration, remove the unregistered `app.id` line and the `BITBUCKET_FORGE_APP_ID` declaration from the manifest, then run `forge register OpenReview` and review its terms in your account. Retain the actual ID assigned by Forge. Do not register an already registered app again: registration creates a new identity. Set the web server's `BITBUCKET_FORGE_APP_ID` to that assigned ARI and `BITBUCKET_FORGE_ENVIRONMENT_ID` to the exact environment ARI from your app's registered environment. Never invent an ID or deploy against a fixture identity.

Run `forge lint`, then deploy/install to an authorized Bitbucket development workspace using the CLI. Grant only the manifest's scopes. `read:pullrequest:bitbucket` includes comment publication. Native opt-in approval and withdrawal additionally require `write:pullrequest:bitbucket`, which also permits broader PR mutations at the platform level. OpenReview uses this scope only for its authenticated app approval/withdrawal endpoints and never merges. Review that expanded scope at installation or upgrade; deploying this source does not grant it. `admin:repository:bitbucket` is included for effective repository permission reads, and also allows repository configuration changes; OpenReview uses it only for authorization reads. Verify these native API fields/permissions on the installed app before activation. No secrets are supplied by the Custom UI; Forge adds signed FIT and OAuth headers to its remote invocation.

In Bitbucket workspace settings → Forge Apps → OpenReview, paste an authorization generated by the target OpenReview workspace admin. The backend independently checks that the native invoking account owns the signed Bitbucket workspace and consumes the one-use code. A connection remains suspended until a signed native event arrives and the hourly token renewal succeeds. In OpenReview Settings → Code providers, an administrator clicks Verify access and activate. Activation rechecks native repository discovery and current authorization, requires event delivery within 24 hours and renewal within 90 minutes, and rejects reconnection/disconnection races. Setup events record delivery proof without scheduling reviews; choose repositories after activation. Refreshing a token or loading this page cannot enable reviews. Installed-app acceptance remains required. Do not edit production suspension flags to substitute for acceptance.

The remote declares storage of in-scope end-user data: authorized repository indexes, review data and encrypted app credentials live on the configured OpenReview backend. Source context is sent to the operator's configured model provider during reviews. The app does not claim Atlassian realm pinning or residency migration support.

Verify native UI submission/recovery, scheduled renewal, all event subscriptions, indexing, reviews, comment follow-ups, revised commits and uninstall. The direct `preUninstall` endpoint clears encrypted credentials and disables selected repositories/index jobs. Forge's uninstall notification is non-blocking: if its delivery fails, uninstall still succeeds. OpenReview's connection can also be explicitly disconnected by an admin; expired tokens fail closed. Do not infer native acceptance from a local static preview or contract test.

See [backend integration and limits](../../docs/bitbucket-cloud.md), [workspace settings module](https://developer.atlassian.com/platform/forge/manifest-reference/modules/bitbucket-workspace-settings-menu-page/), [frontend remote calls](https://developer.atlassian.com/platform/forge/remote/calling-from-frontend/), and [pre-uninstall remote support](https://developer.atlassian.com/platform/forge/manifest-reference/modules/pre-uninstall-trigger/).

## Personal author linking

The manifest also exposes OpenReview identity in workspace personal settings through `bitbucket:workspacePersonalSettingsPage`. It uses a separate personal form and fixed `/api/bitbucket/forge/identity` path. A person first generates a five-minute code in OpenReview Settings → Personal setup, then confirms it while signed in as their native Bitbucket account. The remote verifies the actual human identity and selected repository read access. Encrypted user credentials expire within one hour and require explicit re-confirmation after expiry or app credential renewal; they are never returned to the UI. No additional native scopes are added. The personal page does not offer owner-only workspace installation. Live installed-app testing is still required.

The official npm CLI runner reaches `whoami` and reports Not logged in. The pnpm dlx runner failed in a third-party TypeScript parser; use the official npm runner or vendor-installed CLI rather than altering OpenReview dependencies to compensate. CLI usage analytics is disabled locally.

Atlassian account token management currently requires an emailed eight-digit identity verification before its scoped-token form can be opened. Complete this in the native browser. Then use Create API token with scopes, choose Forge and only the required native development scopes, set a bounded expiry, and complete the separate action-time access confirmation. Keep the token out of chat and logs. For login, use the native OS keychain through `forge login` or environment variables FORGE_EMAIL/FORGE_API_TOKEN as documented by Atlassian. An owner-only ignored local handoff file is prepared at output/setup/forge-auth-private.json; it is not a production deployment file.

Register the existing source with `forge register` only once after reviewing the registration’s developer terms. Do not automatically pass --accept-terms, re-register an existing app, or substitute an OAuth client ID for the Forge ARI. Configure the resulting exact app/environment IDs and OpenReview remote origin, deploy the built UI/manifest, install only to the expressly selected test workspace after native permission confirmation, and verify events/hourly renewal before OpenReview activation.
